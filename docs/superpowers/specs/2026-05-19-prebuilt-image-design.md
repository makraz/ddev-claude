# Pre-built Base Image Design (v0.3.0)

**Status:** Approved (brainstorming) — pending user spec review
**Date:** 2026-05-19
**Targets:** ddev-claude `v0.3.0` (beta first, then stable)
**Base:** ddev-claude `v0.2.0-beta.1`

---

## Goal

Replace the per-project sidecar build with a pre-built, multi-arch Docker image published to GitHub Container Registry. The user's `ddev restart` becomes a fast pull (≈15 s) instead of a 2-minute build, and the Claude Code binary version baked into the image is reproducible and auditable.

## Non-goals

- Per-extra image variants (combinatorial explosion; keep extras as per-project build-time layers).
- A `base_image:` override config key (YAGNI — local-tag override and the escape hatch already cover the niche cases).
- Catalog expansion, IPv6, `read_only` rootfs, DNS-port hardening, new subcommands — all explicitly deferred to later cycles.

## Hard constraints (security model)

The same invariants from the `v0.2.0` spec must hold:

- **Outbound network isolation.** Runtime allow-list unchanged.
- **Filesystem isolation.** Agent runs as uid 1000; sudoers scoped to `init-firewall.sh` only.
- **No privileged escape.** No docker.sock mount, no SSH bridge.

The pre-built image is built in CI from a public Dockerfile in this repo. It does not introduce opaque base layers, third-party dependencies beyond `debian:bookworm-slim`, or any new runtime privileges. The `claude` binary is still installed from `https://claude.ai/install.sh`; the install just happens once on GitHub's runners instead of on every user's machine.

## Architecture overview

One new artifact: a public multi-arch image `ghcr.io/makraz/ddev-claude-base:<version>`, where `<version>` matches the addon's git tag 1:1.

```
ddev-claude/
├── image/                              NEW: source of the published image
│   ├── Dockerfile
│   └── README.md
├── claude/
│   ├── Dockerfile.base                 MODIFIED: thin wrapper (~12 lines)
│   ├── build-image.sh                  UNCHANGED
│   ├── init-firewall.sh                UNCHANGED
│   └── extras/                         UNCHANGED
└── .github/workflows/
    ├── tests.yml                       MODIFIED: build base image locally before bats
    └── publish-image.yml               NEW: build + push on tag
```

**Flow:**

```
Tag push (v0.3.0, v0.3.0-beta.1, …)
        │
        ▼ .github/workflows/publish-image.yml
        │  buildx multi-arch (linux/amd64, linux/arm64)
        ▼
ghcr.io/makraz/ddev-claude-base:<tag>


User runs `ddev restart` (per-project)
        │
        ▼ .ddev/claude/Dockerfile (generated by build-image.sh):
        │
        │   FROM ghcr.io/makraz/ddev-claude-base:v0.3.0
        │   USER root
        │   COPY init-firewall.sh /usr/local/bin/init-firewall.sh
        │   RUN chmod 0755 /usr/local/bin/init-firewall.sh
        │   # {{EXTRAS}}  ← replaced by selected extras
        │   USER claude
        │   WORKDIR /var/www/html
        │
        ▼ docker pull (cached after first) + docker build (thin wrapper + extras)
```

**Latency change (cold cache):**

| Scenario | v0.2.0-beta.1 | v0.3.0 |
|---|---|---|
| Default install (no extras) | ~2 min build | ~15 s pull + ~5 s wrapper ≈ **20 s** |
| With `extras: [php]` | ~3 min build | ~15 s pull + ~45 s extras ≈ **1 min** |

## Components

### `image/Dockerfile` — the published image

Owns everything except `init-firewall.sh` and extras.

```dockerfile
#ddev-generated
FROM debian:bookworm-slim

ENV DEBIAN_FRONTEND=noninteractive

RUN apt-get update && apt-get install -y --no-install-recommends \
      ca-certificates \
      curl \
      git \
      bash \
      sudo \
      iptables \
      ipset \
      dnsmasq \
      dnsutils \
      iproute2 \
 && rm -rf /var/lib/apt/lists/*

ARG USERNAME=claude
ARG USER_UID=1000
RUN groupadd --gid $USER_UID $USERNAME \
 && useradd  --uid $USER_UID --gid $USER_UID -m -s /bin/bash $USERNAME \
 && echo "$USERNAME ALL=(root) NOPASSWD: /usr/local/bin/init-firewall.sh" \
      > /etc/sudoers.d/claude-firewall \
 && chmod 0440 /etc/sudoers.d/claude-firewall

USER claude
WORKDIR /home/claude
RUN curl -fsSL https://claude.ai/install.sh | bash
ENV PATH="/home/claude/.local/bin:${PATH}"

WORKDIR /var/www/html
```

Structurally identical to today's `claude/Dockerfile.base` minus the firewall-script COPY/chmod and the `{{EXTRAS}}` marker.

### `claude/Dockerfile.base` — the thin per-project wrapper

```dockerfile
#ddev-generated
# Pulls the pre-built base image (heavy lifting done in CI) and adds the
# per-addon-release firewall script + extras injection point.
FROM ghcr.io/makraz/ddev-claude-base:v0.3.0

USER root
COPY init-firewall.sh /usr/local/bin/init-firewall.sh
RUN chmod 0755 /usr/local/bin/init-firewall.sh

# ---- EXTRAS INJECTION POINT ----
# build-image.sh replaces the line `# {{EXTRAS}}` below with the concatenated
# contents of every selected claude/extras/<name>.fragment, followed by
# .ddev/claude.local/Dockerfile.fragment if it exists.
# {{EXTRAS}}
# --------------------------------

USER claude
WORKDIR /var/www/html
```

**USER semantics:** the base image leaves `USER claude` set. The wrapper flips to `root` for privileged ops (COPY + chmod + extras' apt installs), then restores `USER claude` + `WORKDIR /var/www/html` at the end — same runtime contract as today. Extras' fragments continue to start under `USER root` (the marker sits inside the root-context block).

**`FROM` tag is hard-coded** to match the addon's release tag. When we cut `v0.3.0`, `Dockerfile.base` ships with `FROM ghcr.io/makraz/ddev-claude-base:v0.3.0`. When we cut `v0.3.1`, the file says `:v0.3.1`. The addon version and the image version are always aligned.

### `.github/workflows/publish-image.yml` — release pipeline

```yaml
name: publish-image

on:
  push:
    tags:
      - 'v*'
  workflow_dispatch:

permissions:
  contents: read
  packages: write

jobs:
  build-and-push:
    name: build & push base image
    runs-on: ubuntu-22.04
    steps:
      - uses: actions/checkout@v4

      - name: Set up QEMU
        uses: docker/setup-qemu-action@v3

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.repository_owner }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Capture Claude Code version
        run: |
          CLAUDE_VERSION=$(docker run --rm debian:bookworm-slim bash -c '
            apt-get update -qq && apt-get install -y -qq curl ca-certificates >/dev/null &&
            curl -fsSL https://claude.ai/install.sh | bash >/dev/null &&
            ~/.local/bin/claude --version
          ' | head -1)
          echo "CLAUDE_VERSION=$CLAUDE_VERSION" >> "$GITHUB_ENV"
          echo "Resolved Claude Code version: $CLAUDE_VERSION"

      - name: Build & push
        uses: docker/build-push-action@v6
        with:
          context: image
          platforms: linux/amd64,linux/arm64
          push: true
          tags: |
            ghcr.io/${{ github.repository_owner }}/ddev-claude-base:${{ github.ref_name }}
          labels: |
            org.opencontainers.image.source=https://github.com/${{ github.repository }}
            org.opencontainers.image.version=${{ github.ref_name }}
            org.opencontainers.image.licenses=MIT
            io.makraz.ddev-claude.claude-version=${{ env.CLAUDE_VERSION }}
```

**Conventions:**
- **One image tag per git tag.** `v0.3.0-beta.1` → `:v0.3.0-beta.1`. `v0.3.0` → `:v0.3.0`. No `:latest`, no `:v0.3`, no floating tags — consumers reference a specific version and pin to it.
- **Multi-arch via buildx** + QEMU. ~3–5 min total runtime in CI.
- **Tag immutability** enforced by convention: git tags are immutable, the workflow refuses to overwrite by design (no retag step exists).
- **Claude Code version captured** in an OCI label so `docker inspect ghcr.io/.../ddev-claude-base:v0.3.0` shows which build is baked in.

### `.github/workflows/tests.yml` — PR/CI validation

The existing test workflow gets one additional step before the bats run, so PRs that touch `image/Dockerfile` can be validated before any image is published:

```yaml
      - name: Build base image locally (for PR validation)
        run: |
          TAG=$(grep -m1 'FROM ghcr.io/.*/ddev-claude-base:' claude/Dockerfile.base | sed 's|.*:||')
          docker build -t "ghcr.io/${{ github.repository_owner }}/ddev-claude-base:${TAG}" image/
```

This builds the image (single-arch — whatever the runner is) with the same tag the addon expects. Docker's default pull policy (`missing`) means subsequent `docker build` / `ddev restart` steps use the local copy. PRs are then validated by the existing bats integration suite without needing the tag in GHCR.

## Data flow

A user's edit-build-run cycle:

```
1. User updates the addon: `ddev add-on get makraz/ddev-claude@v0.3.0`.
   .ddev/claude/Dockerfile.base now contains FROM ghcr.io/...:v0.3.0.
2. User edits .ddev/claude.yaml (if they want extras) and runs `ddev restart`.
3. pre-start-host hook → build-image.sh → generates .ddev/claude/Dockerfile
   from Dockerfile.base + selected extras (unchanged logic from v0.2.0).
4. docker-compose triggers a build:
   - docker pull ghcr.io/.../ddev-claude-base:v0.3.0   (~15 s first time)
   - docker build of the thin wrapper                   (~5–60 s by extras)
5. Sidecar starts with `sleep infinity`.
6. `ddev claude` activates firewall + opens session — unchanged from v0.2.0.
```

State at `.ddev/.claude/` is untouched by the upgrade — same uid 1000, same `/home/claude/.claude` mount target.

## Versioning and pinning

- Image tag = addon git tag. 1:1 always.
- Beta releases (`v0.3.0-beta.N`) also publish images, also pre-released on GitHub, also pinned in the addon's `Dockerfile.base` for that beta.
- No `:latest` tag movement. Users see exactly what they pinned.
- Claude Code binary version is whatever `https://claude.ai/install.sh` resolves to at image build time, recorded in `io.makraz.ddev-claude.claude-version` label on the image.

## Dev workflow

**Iterating on `image/Dockerfile` locally:** Docker's default pull policy is `missing`, so a local build with the same tag wins:

```bash
docker build -t ghcr.io/makraz/ddev-claude-base:v0.3.0 image/
ddev restart   # uses local build, no GHCR fetch
```

That's the whole dev loop. No new flags, config keys, or fallback modes.

**Forking the base image** (e.g., corporate root certs, alternative distro): two existing mechanisms cover this without new addon code.

1. Local-tag override: build your own image with the same tag in your Docker cache.
2. Extend via escape hatch: drop a `.ddev/claude.local/Dockerfile.fragment` that adds your customizations on top.

## Error handling

Failure modes and behaviors:

| Scenario | Behavior |
|---|---|
| GHCR is unreachable from the user's network | `docker pull` fails with a clear network error during `ddev restart`. No silent fallback. |
| The pinned image tag was never published (e.g., consuming a not-yet-released addon version from a local checkout) | `docker pull` fails with manifest unknown. Solution: build the image locally with the right tag (Dev workflow above). |
| `image/Dockerfile`'s Claude Code installer fails during CI | `publish-image.yml` job fails; no image published; no release created on GitHub. Existing v0.x users unaffected. |
| User edits `Dockerfile.base` directly | `ddev add-on get` overwrites it on the next upgrade (file is `#ddev-generated`). User-managed override path: `.ddev/claude.local/Dockerfile.fragment`. |
| GitHub Actions runner runs out of disk during arm64 emulation | Workflow fails. Re-run by re-pushing the tag (delete + re-create the git tag). |

## Testing

Existing tests are preserved as-is; one new CI step ensures PRs always have an image to test against.

| Layer | File | Change |
|---|---|---|
| Unit | `tests/build-image.bats` | Unchanged. The wrapper assembly is the same. |
| Integration | `tests/test.bats` | Unchanged. Exercises pull + wrapper build + extras + firewall + CLI + state lifecycle end-to-end. |
| CI image build | `.github/workflows/tests.yml` | One step added: build the base image locally before bats runs. |
| Publish | `.github/workflows/publish-image.yml` | New workflow. Validates the image builds for amd64 + arm64 on every tag push. |

No new bats tests are required. The "agent runs commands as uid 1000 in the firewalled sandbox" property is what all the existing tests assert, and that property holds regardless of whether the image was pre-built or built per-project.

## Release sequence

1. PRs land on `main` updating `claude/Dockerfile.base`'s `FROM` to the next planned tag (e.g., `:v0.3.0-beta.1`).
2. `git tag v0.3.0-beta.1 && git push origin v0.3.0-beta.1`.
3. `publish-image.yml` fires, builds + pushes `ghcr.io/makraz/ddev-claude-base:v0.3.0-beta.1` for amd64+arm64.
4. `gh release create v0.3.0-beta.1 --prerelease --title "v0.3.0-beta.1" --notes ...`.
5. Beta testers install via `ddev add-on get makraz/ddev-claude@v0.3.0-beta.1`.
6. Iterate beta tags if needed.
7. When stable: bump `Dockerfile.base` to `:v0.3.0`, tag `v0.3.0`, push. Image builds, non-prerelease GitHub release created. Marked Latest manually.

## Open issues / future work

- **`base_image:` config key** for forks. Skipped now; reconsider if real demand surfaces.
- **Cosign / sigstore signatures** on the published image for supply-chain verification. Stretch goal.
- **Image scanning** (Trivy / grype) in CI. Useful before stable v0.3.0 lands.
- **GHCR retention policy** — old beta images accumulate. A periodic cleanup workflow (keep last N beta tags, all stable tags) avoids registry bloat. Not blocking v0.3.0.
- The deferred items from v0.2.0's spec (read_only rootfs, DNS-port restriction, catalog growth, `ddev claude logs`/`status`) remain on the future-work list.
